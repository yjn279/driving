## この文書の構成

仕様を 2 つのレイヤーに分けています。

| レイヤー | 何を書くか | 接頭辞 |
| :-- | :-- | :-- |
| ビジネス要件 | ユーザーが何を得られるか。なぜこのアプリが要るか | `BR` |
| システム要件 | ビジネス要件を満たすために、システムが何をどう行うか | `SR` |

**すべてのシステム要件は、いずれかのビジネス要件に属します。**
識別番号は `SR-<所属するビジネス要件の番号>-<連番>` の形で、番号だけで親が分かります。
たとえば `SR-03-08` は `BR-03` を満たすための 8 番目のシステム要件です。

親を持たないシステム要件は置きません。どのビジネス要件にも紐づかない決めごとが現れたら、
それは仕様ではなく実装の都合か、書き漏らしたビジネス要件のどちらかです。

各識別番号は[テスト内容](/developer/testing)から参照します。

## 1. ビジネス要件

### 1.1 満たすこと

| ID | ビジネス要件 | 理由 |
| :-- | :-- | :-- |
| `BR-01` | 走行中の荷重が、どの向きへどう移り変わったかを後から振り返れる | 荷重コントロールの上達とは、大きな G を出すことではなく、G を途切れさせずに繋ぐこと。その繋がりは走りながらでは分からない |
| `BR-02` | 最大 G やスコアを主役にしない | 大きな G を出すことは上達ではない。数値を競わせると、見るべきものから目が逸れる |
| `BR-03` | 記録した荷重の向きが、運転者の体感と一致する | 向きが違えば、記録されたデータのすべてが意味を失う |
| `BR-04` | 走行全体を俯瞰して、どこで G がかかっていたかが一目で分かる | 振り返る場所を自分で見つけられるようにする |
| `BR-05` | 気になった地点を選び、その前後の荷重の移り変わりを掘り下げられる | 俯瞰で見つけた場所を、コーナー 1 つ単位で確かめる |
| `BR-06` | 過去の走行を一覧から呼び出し、不要なものを消せる | 振り返りは走行直後とは限らない |
| `BR-07` | 走行時間と距離を、セッションごとと累計で把握できる | どれだけ練習したかが分かる |
| `BR-08` | サーバーを使わず、記録はすべて端末内に留まる | 個人利用であり、走行の記録は生活圏の情報を含む |
| `BR-09` | 車載で長時間走っても、記録が破綻せず端末が消耗しない | 実際の使用は数十分から数時間に及ぶ |
| `BR-10` | 運転中に画面を注視せずに使える | 運転者が使うため。安全に関わる |

要望が出るまで実装しません。

| ID | 作らないもの |
| :-- | :-- |
| `SCP-01` | 4 輪個別の荷重計算モデル |
| `SCP-02` | スコアリング、ランキング、ゲーミフィケーション |
| `SCP-03` | SNS 共有、クラウド同期、アカウント機能 |
| `SCP-04` | ドラレコ映像との同期 |
| `SCP-05` | Android 対応 |
| `SCP-06` | 走行中の音声コーチング |

## 2. システム要件

### 2.1 BR-01 — 荷重の移り変わりを振り返れる

実装は `src/core/vehicle-frame.ts` ・ `src/ui/GGDiagram.tsx` にあります。

| ID | システム要件 | 理由 |
| :-- | :-- | :-- |
| `SR-01-01` | 荷重は加速度の逆向き（`load = -a`）とし、表示はすべて荷重ベクトルで行う | 運転者が体で感じるのは加速度ではなく、その反作用として体や車体にかかる荷重である |
| `SR-01-02` | G-G ダイアグラムは縦軸の上を前荷重、横軸の右を右荷重とする | 荷重が前後左右斜めのどこにかかっているかを 1 枚で表せる |
| `SR-01-03` | 選択点の前後 3 秒の荷重を、点ではなく軌跡として描く | コーナー 1 つ分の荷重の移り変わりが収まる長さ |
| `SR-01-04` | 軌跡は古い点ほど薄く、新しい点ほど濃く描き、選択時刻の位置に印を置く | 時間の流れとして読めるようにする |

#### 運転操作と荷重の向き

| ID | 運転操作 | 車両の加速度 | 荷重の向き |
| :-- | :-- | :-- | :-- |
| `SR-01-05` | ブレーキ | 後ろ | **前** |
| `SR-01-06` | 加速 | 前 | **後ろ** |
| `SR-01-07` | 右コーナー | 右 | **左** |
| `SR-01-08` | 左コーナー | 左 | **右** |

### 2.2 BR-02 — 最大 G を主役にしない

| ID | システム要件 | 理由 |
| :-- | :-- | :-- |
| `SR-02-01` | 最大 G の数値の強調表示や、ランキング的な演出を画面に置かない | 目を引く数値があると、そこが目的になってしまう |

### 2.3 BR-03 — 荷重の向きが体感と一致する

実装は `src/core/calibration.ts` ・ `src/core/vehicle-frame.ts` ・ `app/record.tsx` にあります。

| ID | システム要件 | 理由 |
| :-- | :-- | :-- |
| `SR-03-01` | 運動の入力には DeviceMotion の `acceleration`（重力を除いたユーザー加速度、m/s²）を使う | 重力の分離を iOS の統合処理に任せられる |
| `SR-03-02` | 重力方向の取得には `accelerationIncludingGravity` を使う | 静止時にはこれがそのまま重力ベクトルになる |
| `SR-03-03` | 車両座標系は右手系とする。`forward` は前方、`right` は右方、`up` は鉛直上向きで、`right = forward × up` | 3 軸の関係を 1 つの式で決めておくと、左右の取り違えが起きない |
| `SR-03-04` | 静止フェーズの平均から `up = -normalize(重力ベクトルの平均)` を求める | 座標系の起点。ここが崩れると以降のすべての計算が意味を失う |
| `SR-03-05` | 較正は静止 → 加速 の 2 段階で行う | 重力だけでは前後軸が決まらないため、直線加速の向きを「前」として補う |
| `SR-03-06` | 静止の成立条件は、直近 2 秒間の 3 軸すべてで標準偏差が 0.15 m/s² 以下であること | アイドリングの振動は通し、車が動いている状態は通さない大きさ |
| `SR-03-07` | あわせて、その 2 秒間の平均のノルムが 9.81 ± 0.5 m/s² に収まること | 重力以外の力が働いていないことの担保 |
| `SR-03-08` | 加速の成立条件は、直近 1 秒間の水平成分の平均が 0.5 m/s² 以上であること | 時速 10 km まで 10 m ほど進むだけで成立する大きさ。10 m で時速 10 km に達する等加速度は 0.39 m/s² で、発進の立ち上がりはこれより強い |
| `SR-03-09` | あわせて、判定窓の前半と後半それぞれの平均方向のずれが 30 度以内であること | 曲がりながらの加速を弾く。平均どうしの比較なのでノイズは打ち消し合う |
| `SR-03-10` | 判定はサンプル 1 つずつではなく、判定窓をならした値に対して行う | 走行中は路面の凹凸とセンサーのノイズが 1 サンプルごとに乗る。全サンプルに閾値を課すと、まっすぐ加速していても外れ値 1 つで不成立になる |
| `SR-03-11` | 条件を満たさない場合は、推定値で先へ進めず、明示的にやり直しを求める | ここで妥協した値を採ると、以降の記録がすべて無意味になる |
| `SR-03-12` | 確認の段階で、「ブレーキで矢印が前を向く」と「右コーナーで矢印が左を向く」の両方を確かめさせる | 前後だけでは足りない。重力の向きを取り違えると、前後は正しいまま左右だけが入れ替わるため、ブレーキの確認では気づけない |
| `SR-03-13` | 較正の結果は保存・再利用せず、走行ごとに取り直す | 車載ホルダーへの取り付け角度は毎回わずかにずれる |
| `SR-03-14` | 加速フェーズでは、判定に使っている現在の水平加速度を画面に表示する | 何をどれだけ強く行えばよいか分からないまま待たされることを避ける |
| `SR-03-15` | 端末座標系から車両座標系への回転行列は、走行中を通じて一定とする | 端末は車体に固定して使うため、両者の関係は走行中に変わらない |
| `SR-03-16` | 坂道での車体のピッチ・ロールに対する補正は行わない | 勾配による重力の漏れ込みは `SR-03-01` の時点で既に取り除かれている。iOS が加速度計・ジャイロ・地磁気を統合して重力成分を推定し、差し引いた値を返すため |

`SR-03-16` に残る誤差は、サスペンションの沈み込みやロールによって車体が路面に対して傾く分です。
数度の範囲に収まり、これを補正するにはサスペンションの特性を入力させる必要があります。
得られる精度に対して要求が重すぎるため、補正しません。

減速を「前」と取り違える恐れは小さいといえます。判定は静止フェーズの直後、つまり停車状態から
動き出したところで行うため、停止状態から減速は起こらず、発進の加速が先に条件を満たすからです。

### 2.4 BR-04 — 走行全体を俯瞰できる

実装は `src/ui/g-color.ts` ・ `app/session/[id].tsx` にあります。

| ID | システム要件 | 理由 |
| :-- | :-- | :-- |
| `SR-04-01` | ルートは合計 G（`sqrt(ax² + ay²)` を g 単位にした値）で 5 段階に色分けする。境界は 0.1 / 0.2 / 0.3 / 0.4 g | 日常的な市街地走行から強い減速・旋回までを見分けられる刻み |
| `SR-04-02` | 同じ境界を地図の凡例として画面に表示する | 色が何 G を指すのかを読み取れるようにする |

### 2.5 BR-05 — 地点を選んで掘り下げられる

| ID | システム要件 | 理由 |
| :-- | :-- | :-- |
| `SR-05-01` | 地図のタップはもっとも近い記録位置を選ぶ。ルートから 100 m を超えて離れている場合は選択しない | 細い折れ線を指で正確に押すのは難しい |

### 2.6 BR-06 — 過去の走行を呼び出せる

実装は `app/index.tsx` ・ `src/db/sessions.ts` にあります。

| ID | システム要件 | 理由 |
| :-- | :-- | :-- |
| `SR-06-01` | セッションを一覧で表示し、行から削除できる | 振り返りの入口であり、不要な記録の掃除口でもある |
| `SR-06-02` | 停止の処理が走らなかったセッション（`ended_at` が NULL）は、次に一覧を開いたときに削除する | 走行時間も距離も 0 のまま残ると累計が歪む |

### 2.7 BR-07 — 走行実績を把握できる

実装は `src/core/distance.ts` ・ `src/db/sessions.ts` にあります。

| ID | システム要件 | 理由 |
| :-- | :-- | :-- |
| `SR-07-01` | セッションごとの走行時間と走行距離を記録し、一覧に表示する | 1 回ごとの実績 |
| `SR-07-02` | 全セッションの走行時間と走行距離の累計を表示する | 積み上げた練習量 |
| `SR-07-03` | 走行距離は、連続する 2 つの記録位置の haversine 距離を積算して求める | 地球を球とみなす近似で、市街地の走行距離には十分な精度が得られる |

### 2.8 BR-08 — 記録は端末内に留まる

実装は `src/db/schema.ts` にあります。

| ID | システム要件 | 理由 |
| :-- | :-- | :-- |
| `SR-08-01` | 記録は端末内の SQLite に保存し、外部へ送信しない | サーバーを持たない |
| `SR-08-05` | `locations` と `accelerations` に `(session_id, t)` の索引を張る | 時刻範囲での取り出しを速くする |
| `SR-08-06` | `session_id` は `sessions.id` への外部キーとし、セッションの削除で紐づく行も連鎖削除する | 削除の取りこぼしを仕組みで防ぐ |

#### 表の構成

| ID | 表 | 列 |
| :-- | :-- | :-- |
| `SR-08-02` | `sessions` | `id` ・ `started_at` ・ `ended_at` ・ `duration_ms` ・ `distance_m` |
| `SR-08-03` | `locations` | `session_id` ・ `t` ・ `lat` ・ `lon` |
| `SR-08-04` | `accelerations` | `session_id` ・ `t` ・ `ax` ・ `ay` |

### 2.9 BR-09 — 長時間走っても破綻しない

実装は `app/record.tsx` ・ `src/db/samples.ts` にあります。

| ID | システム要件 | 理由 |
| :-- | :-- | :-- |
| `SR-09-01` | 加速度は 50 Hz で取得する | G-G 軌跡の滑らかさが判別できる。これ以上上げても軌跡の見え方は変わらない |
| `SR-09-02` | 位置情報は 1 Hz で取得する | ルート描画と距離計算に十分 |
| `SR-09-03` | 加速度はコールバックごとに保存せず、メモリ上のバッファへ積み、5 秒ごとに 1 トランザクションでまとめて書き込む | 書き込み回数を 250 分の 1 に抑えつつ、異常終了で失う量を 5 秒以内に留める |
| `SR-09-04` | 保存するのは車両座標系へ変換した後の `ax` ・ `ay` のみとし、上下方向は保存しない | G-G ダイアグラムは水平 2 軸しか使わない |
| `SR-09-05` | 読み出しは時刻範囲で必要な分だけ行い、セッション全件をメモリに載せる処理を設けない | 1 時間の走行で加速度は 18 万件になる |
| `SR-09-06` | 荷重の表示の更新は 10 Hz に間引く | センサーは 50 Hz で届くが、届いたサンプルごとに描き直すと発熱と電池の消耗が増える |
| `SR-09-07` | 記録中は画面の消灯を抑止し、停止時に解除する | 記録は前面でのみ動くため、消灯すると記録が止まる |

### 2.10 BR-10 — 運転中に画面を注視しない

| ID | システム要件 | 理由 |
| :-- | :-- | :-- |
| `SR-10-01` | 較正の各段階は、条件を満たした時点で自動的に次へ進む | 運転中にボタンを押させない |
| `SR-10-02` | 記録中の表示は、荷重の向きと大きさ・経過時間・走行距離の 3 つに限る | 見るものが少ないほど、目を戻す時間が短い |

## 3. 受け入れ基準

完成したと判断する条件です。実機での走行によって確かめます。

| ID | 基準 | 対応するビジネス要件 |
| :-- | :-- | :-- |
| `ACP-01` | 較正後、実走行で G の向きが体感と一致する | `BR-03` |
| `ACP-02` | 走行後、地図上に色分けされたルートが表示される | `BR-04` |
| `ACP-03` | コーナーをタップすると、そのコーナーでの G-G 軌跡が見られる | `BR-01` `BR-05` |
| `ACP-04` | 過去の走行を一覧から呼び出せる | `BR-06` |
| `ACP-05` | セッションごとと累計の走行時間・距離が表示される | `BR-07` |
